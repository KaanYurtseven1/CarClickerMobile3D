## SECTION 5 — POSSIBLE HIERARCHY / INSPECTOR MISTAKES TO WATCH FOR

### CRITICAL Issues

#### 1. SFXManager DontDestroyOnLoad on a Child Object

**Risk: HIGH**

SFXManager sits at `SYSTEMS → Managers → SFXManager` (nested 2 levels deep). Its `Awake()` calls `DontDestroyOnLoad(gameObject)` without detaching from its parent first.

**What actually happens in Unity 2021+:** When you call `DontDestroyOnLoad()` on a child object, Unity applies it to the **root** ancestor. So `SYSTEMS` (the root) and its entire subtree (including Managers, PoliceChaseFeedbackController, CardManager, etc.) all get moved to DontDestroyOnLoad.

**Why this "works":** The entire SYSTEMS tree persists across scene loads. SFXManager survives → works correctly. PoliceChaseFeedbackController also survives → events still fire.

**Risk:** If you ever reorganize SYSTEMS or add non-persistent objects under it, they'll also persist unexpectedly. Unity also logs a console warning every time.

**Recommendation:** Consider adding parent detachment to SFXManager's Awake (like GameManager and SaveSystem already do):

```csharp
if (transform.parent != null)
    transform.SetParent(null);
DontDestroyOnLoad(gameObject);
```

This is NOT a blocking issue for now — the current setup works because the SYSTEMS hierarchy is stable.

#### 2. Duplicate Singleton on Scene Reload

**Risk: MEDIUM**

When returning to Main.unity from another scene (e.g., ChestOpenScene → Main), the scene's SFXManager, PoliceChaseFeedbackController, etc. are re-instantiated from the scene data. The DDOL copies from the first load also still exist.

**What prevents this:** Each singleton's `Awake()` checks `if (Instance != null) { Destroy(gameObject); }`. The new duplicates self-destruct. This is correct.

**Watch for:** If a singleton Awake runs before the DDOL Instance is ready, you could get a race condition. In practice, this doesn't happen because DDOL objects are always initialized before scene objects.

#### 3. MusicManager Placed as Child Instead of Root

**Risk: HIGH if wrong**

MusicManager MUST be a **root-level** GameObject. If you accidentally parent it under Managers or any other object, `DontDestroyOnLoad(gameObject)` will either:

- Fail silently
- Apply to the wrong root ancestor

**Fix:** Always verify MusicManager has no parent in the Hierarchy. It should appear at the same indent level as SYSTEMS, GAMEPLAY, CAMERAS, etc.

#### 4. AudioListener Conflicts

**Risk: MEDIUM**

Unity warns when multiple AudioListeners are active simultaneously. Currently:

- Main.unity: Main Camera has AudioListener (enabled), SnapshotCamera has AudioListener (disabled) ✅
- ChestOpenScene: ChestOpenCamera has AudioListener ✅
- NewGarage: Camera has AudioListener ✅
- TakeTheCarScene: Camera has AudioListener ✅

**Risk scenario:** If Main Camera persists via DontDestroyOnLoad (e.g., as part of CAMERAS root), there would be 2 active AudioListeners when loading ChestOpenScene (Main Camera + ChestOpenCamera).

**Verify:** Does the Main Camera / CAMERAS root survive scene transitions? If it does, disable the local scene cameras' AudioListeners, or destroy the DDOL camera on scene change. If Main Camera does NOT persist (scene-local only), this is not an issue.

#### 5. BoostAudioController on Wrong GameObject

**Risk: LOW**

BoostAudioController MUST be on the same GO as BoostModeController. If placed on a different object, it will still work (it uses `BoostModeController.Instance` to subscribe), BUT it won't travel with BoostModeController when it detaches and calls DontDestroyOnLoad.

**Consequence if placed wrong:** BoostAudioController would be destroyed on scene change and stop working.

**Fix:** Always add it directly on the BoostModeController GO (under GAMEPLAY → CardControllers → BoostModeController).

#### 6. Missing Clip Assignments (Silent Failures)

**Risk: LOW (no crashes, just silence)**

All `PlayXxx()` methods in SFXManager have null-checks:

```csharp
if (!sfxEnabled || clip == null || sfxSource == null) return;
```

If a clip field is left null, that SFX simply won't play. **No NullReferenceException will occur.** But you'll get silence where audio should be.

**Tip:** After assigning all clips, search the SFXManager Inspector for any remaining "None (Audio Clip)" fields. Every field under every header should have a clip assigned.

#### 7. PoliceChaseFeedbackController AudioSources Missing

**Risk: HIGH if you want chase audio**

The PoliceChaseFeedbackController currently has **zero** AudioSource components and **zero** child objects. If you skip creating the 5 child AudioSources, ALL chase audio (stinger, loop, heartbeat, siren, engine) will be completely silent — but the code won't crash because it null-checks each source.

The `gameplayMusicSource` field should be left **null** — MusicManager now handles music ducking separately.

#### 8. loopSFXSource Conflict Between Rain and Boost

**Risk: LOW**

SFXManager uses a single `loopSFXSource` for both rain loops and boost loops. If rain is playing and boost activates simultaneously, `StartBoostLoop()` will replace the rain loop clip.

**Mitigating code:** `StopBoostLoop()` checks `if (loopSFXSource.clip != boostActiveLoopClip) return;` to avoid killing a different loop. Similarly, `StopRainLoop()` just fades and stops whatever is playing.

**In practice:** Rain and boost don't overlap in normal gameplay flow. If they ever do, boost takes priority (which is correct behavior). No action needed.

#### 9. Volume Discrepancy Between SFXManager and MusicManager

**Risk: LOW**

SFXManager uses PlayerPrefs key `"SFXVolume"` and MusicManager uses `"MusicVolume"`. These are independent. If you later add a settings UI, make sure to expose both sliders.

Default volumes:

- SFXManager: `_userVolume = 1.0` (full volume one-shots)
- MusicManager: `baseVolume = 0.35`, `_userVolume = 1.0` → effective volume = 0.35

This means music starts at 35% and SFX at 100%. If music feels too quiet or SFX too loud, adjust `baseVolume` in MusicManager's Inspector.
